## Implementation-readiness verdict

## `READY FOR BUILD 1 AFTER SPECIFIC BLOCKERS`

Three A findings and ten B findings. All are narrow. None requires reopening Technical Architecture v1.0, and none is an architecture disagreement — every one is a case of an artifact contradicting a spec that already answers the question correctly.

**Answer to the primary question:** a competent coding agent could implement Build 1 and Build 2 from the *specifications* without inventing a structurally important decision, with one exception (the application language, A1). The specification chain is genuinely closed. Architecture v1.0 defines the object model, workflow states, gate classes, and hash projections. Claims Policy v0.1 §22 and §25 give the deterministic gate list and the required enums. Evidence Package v0.2 §9/§10/§23 give the claim, exposure, and hashing contracts. Writing v0.2 §7/§20.2/§22 give the script object, the diff lock, and the pre-audit gates. Performance & Render v0.1 §23/§24 give the base request hash and its conformance tests. Showrunner Planning v0.1 §6/§13/§23 give the brief shape, the block plan, and the planning gates. I looked for a required decision with no owner and did not find one.

The agent could *not* implement Build 2 from the **frozen fixture**, and the fixture is what the Coding Handoff points it at as the executable contract. The fixture contradicts the specs at nearly every artifact. That is the whole of this review's negative result, and it has a clean explanation: the Cross-Spec Consistency Report's own sequencing put "freeze the walking-skeleton fixture" at step 3 of 5, *after* the cross-spec review completed. The fixture is the only artifact in the corpus that has never been red-teamed against the documents it is supposed to embody.

## 1. Executive summary

- **The specs are done.** Every conditional question I raised against the incomplete pack is answered by a document in this one, usually more precisely than I'd have asked for. Do not reopen them.
- **The fixture is the problem, and it is one work item.** Of 13 findings, 11 are the frozen fixture disagreeing with an active spec. Two are genuine spec-level items (A1, B9).
- **`base_request_hash` is computed as `sha256(the render-block object)`.** Architecture v1.0 (*"Do not hash an entire database object for convenience"*) and Performance & Render §23 both forbid exactly this. Verified: rewriting `t01` leaves `rb01`'s hash byte-identical, and because `t01`/`pb01`/`rb01` are script-local IDs reused every episode, every episode's first Tully block hashes to the same value.
- **`package_hash` omits the spec's domain prefix and hashes `frozen_at`.** Evidence Package §23 requires `sha256("evidence-package-v2\n" + canonical_json(semantic_manifest))` and §4.6 forbids execution timestamps from changing the hash. Verified: two semantically identical packages one second apart hash differently, failing the Contract Trace's own invariant test.
- **Both hash defects land in Build 1**, not Build 2, because Build 1 delivers the canonical hashing library and its done-when is *"reproduce the expected hashes."* The fixture README instructs the agent to recompute and match stored values — so the agent is directed to implement the wrong contract.
- **The fixture's claims carry no `value` field**, so Claims Policy §22.4 (value support) and Writing §22.1 (*"an exact numeric span does not match its supporting allowed claim"*) — both hard deterministic gates — cannot be implemented against it. Three of five claim `kind`s and all five `state`s are outside the required registries.
- **Every single performance-direction value is outside the Performance & Render §6.1 vocabulary**, and the artifact's shape is a per-turn triple where the spec specifies per-intent rows with `scope_type`/`intent_type`/`value`.
- **The fixture fails 6 of the 13 items its own Contract Trace §1 requires it to contain** — including a second program block, which makes the `cross_program_render_block` negative vector unconstructible (there is no `pb02`).
- **Program blocks are defined in the script, not the brief** — a lower layer owning a higher layer's object. Underneath it, `program_blocks[]` appears in both the brief shape and the script shape across two active specs; Architecture resolves it by precedence, but the fixture picked the losing side.
- **Cross-spec patch B1 (Character Bible "we") was applied incompletely.** The errata paragraph landed; the two contradicting passages did not. The project's own review classified this a Build-2 blocker.

## 3. Build-1 ambiguity list

Structurally important questions a coding agent would still have to invent an answer to:

1. **What language and runtime?** (A1.) Nothing in the corpus says. Everything else in Build 1 depends on it.
2. **Which canonical hash contract is authoritative — the specs or the fixture?** (A2, A3.) Build 1's done-when is "reproduce the expected hashes" and the fixture README says to match stored values; the specs say something different. The agent is directed toward the wrong answer.
3. **Which parent owns `program_blocks`?** (B5.) Architecture and Showrunner say the brief; Writing §7 and the fixture say the script. This is a foreign key in the first migration.
4. **Does `script_versions` need `revision_parent_id` in the initial schema?** (B6.) Writing §21 says yes; the fixture shows one flat script. Retrofitting a self-referential FK after rows exist is the expensive version.
5. **What is the uniqueness scope of `base_request_hash`?** (A3.) Global content-address, or scoped per manifest/attempt? The unique index on `render_takes(base_request_hash, take_index)` is written in Build 1, and A3's ID-based projection makes global scope actively unsafe.

Everything else I expected to be open is answered. Architecture settles run/attempt cardinality, immutability, workflow states, gate classes, object storage (R2), the durable workflow mechanism, and which tables Build 1 needs. Those are not questions.

## 5. Fixture verdict

**Misleading — must be rebuilt.** Not "safe after named corrections."

I reached for the middle option and could not defend it. The threshold for "named corrections" is that the fixture teaches the right architecture imperfectly. This one teaches the wrong architecture in the specific places where the specs took the most care:

- Architecture v1.0's resolution of red-team finding **N12** was *"TTS hash too object-wide → explicit render-affecting field projection."* The fixture hashes the whole object. It re-creates the exact defect the architecture was amended to close.
- Architecture's resolution of **N4** was *"gates not bound to judged artifact → gate input fingerprints."* The fixture's manifest binds `audit_id` and drops the fingerprint.
- Architecture's resolution of **N5** was *"usage gate lacks how/where claim was used → span-level uses with use modes."* The fixture uses string spans with no offsets and claims with no values, so the span cannot be checked against the value.
- Architecture's resolution of **N13** was *"mutable chosen takes → immutable render takes + take selections."* The fixture contains no take, selection, assembly map, or master.

Four of the architecture's own resolved findings are un-resolved inside the executable contract the agent is told to implement against. Combined with the fixture README's instruction to recompute hashes and match stored values, and Eng. Standards §2's prohibition on weakening tests, the agent's likely path is to encode the pre-N12 architecture and certify it green.

**What survives the rebuild:** the upstream shape is sound and worth keeping as the skeleton of v0.2 — the claim/brief/script/direction chain, the beat and context-selection structure, the editorial content, the negative-vector *concept*, and the five top-level hashes (which reproduce exactly and only need the domain envelope from A2). The fictional Northbridge/Southbank subject is a good call and should stay.

**What has to be built rather than patched:** the render-manifest half, all four post-audit artifact types, the performance-direction artifact, the negative-vector set, and the claim records. Rebuilding to Contract Trace §1 and §3 is the cleanest route — it is already a checklist, it was written before the fixture, and following it would have prevented most of this.

One structural suggestion: the fixture should ship with a conformance test that validates each artifact against its owning spec's field list and enums, run in CI. Every finding in this review except A1 and B9 would have been caught by that test on the day the fixture was frozen.

Correctly deferred. A reviewer might demand these; they should not be built now.

Nothing here is an architecture problem, and the honest summary is that the documents are ready and the one artifact that was never reviewed is the one that isn't.
